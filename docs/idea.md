# Language-Driven Pick-and-Place Agent

A simulated robot arm that follows natural-language commands, built from the bottom up: a scripted expert, imitation learning, a fine-tuned vision-language-action (VLA) model, reinforcement learning, and an LLM/VLM agent layer. Each layer is benchmarked against the one below it on the same tasks and seeds.

---

## 1. Overview

**Motivation.** Most manipulation projects demonstrate a single technique. This one builds the full stack in one simulator and measures each layer against the one below it on the same tasks and seeds. That makes it possible to attribute failures to perception, planning, or execution.

**Focus.** Robot learning and foundation models: imitation learning, VLA fine-tuning, RL, and LLM/VLM agents. The project contains no kinematics, dynamics, or control code. An off-the-shelf IK library (`mink`) maps end-effector targets to joint targets, and MuJoCo's position servos track them.

**Reference hardware.** A single Apple Silicon laptop (M3 Pro, 36 GB unified memory; see §6.3 for an 18 GB fallback). No robot and no NVIDIA GPU are required. A rented GPU is optional and used only for specific long runs.

**What the project covers.**

| Area | Where |
| --- | --- |
| Simulation environment | Phases 0-1: MuJoCo scene, Gymnasium environment, and a scripted expert built on off-the-shelf IK |
| Reinforcement learning (expert) | Phase 1b: PPO trained from scratch into a stronger expert and demonstrator, replacing the scripted expert as the data source for imitation learning |
| Imitation learning | Phase 2: BC, ACT, and Diffusion Policy with LeRobot, trained on the Phase 1b RL expert's demonstrations |
| Vision-language-action models | Phase 2: SmolVLA fine-tuned on the Phase 1b RL expert's demos, compared with ACT and with the modular agent; Phase 4: SmolVLA as the agent's skill executor |
| Reinforcement learning (refinement) | Phase 3: residual RL refining the Phase 1b RL expert under perturbed dynamics |
| Language and vision agents | Phase 4: VLM grounding, LLM planner, verifier with recovery |
| Reproducible evaluation | A cross-layer benchmark with confidence intervals, one-command regeneration, and a test suite |
| Commodity hardware | Simulation only, CPU physics, small image policies on MPS, quantized local models via MLX, API models for the upper-bound rows |

## 2. Goals and success criteria

**Done means all of the following exist:**

1. A public repo where `make setup && make smoke` finishes in under 30 minutes from a clean clone. This excludes model-weight downloads and training. The smoke target runs the unit tests and one episode per layer.
2. Unit tests for the environment: determinism, success predicates, and camera projection.
3. A benchmark table comparing the scripted expert, BC, ACT (plus Diffusion Policy if not cut), SmolVLA, residual RL, and pure RL on shared tasks and seeds. It reports 95% confidence intervals and is generated by one script.
4. An agent ablation (oracle vs VLM perception, local vs API models) with a failure taxonomy, plus an executor comparison: planner + scripted skills, planner + SmolVLA skills, and SmolVLA end to end.
5. An agent demo video (about 2 minutes): a typed instruction, the plan, the execution, and one real failure with its recovery.
6. A technical write-up (README plus report) with ablations and a limitations section.

**Non-goals.** Real hardware, sim-to-real transfer, novel algorithms, a production system, collision-aware motion planning beyond simple approach and retreat waypoints, implementing kinematics, dynamics, or controllers (an IK library and MuJoCo's position servos handle motion), and training VLAs from scratch.

## 3. Key design decisions

Each decision is recorded, with its rationale, in `docs/decisions.md`.

### 3.1 Robot: Franka Panda by default

Use the **Franka Emika Panda** from MuJoCo Menagerie (`franka_emika_panda/`). The folder contains `panda.xml` (arm plus hand), `panda_nohand.xml`, `hand.xml`, `scene.xml`, and an MJX single-cube scene.

- The gripper is included and already tuned, so there is no integration work.
- The Panda is the most common arm in manipulation-learning work (robosuite, ManiSkill, MuJoCo Playground pick-cube), which makes results easy to compare.

**Alternative:** a UR5e (6-DOF) with a Robotiq 2F-85, joined with `MjSpec.attach`. One robot is used for all reported experiments.

### 3.2 Motion: off-the-shelf IK

The project writes no kinematics or control code. **`mink`**, a differential-IK library built on MuJoCo, converts TCP targets to joint targets, and Menagerie's built-in **position servos** track them. Run IK on a separate robot-only model and copy the robot joint positions from the simulation each tick, so free-floating objects never enter the IK problem.

Also add a **TCP site** between the fingertips. That site is the `ee` frame.

### 3.3 Control hierarchy and rates

| Layer | Rate | Output |
| --- | --- | --- |
| Physics (`implicitfast`, the Panda model's default) | 500 Hz (dt = 2 ms) | state |
| Joint control: MuJoCo position servos | 500 Hz, every physics step | joint torques |
| IK (`mink`) and waypoint interpolation | 100 Hz (every 5 physics steps) | joint position targets |
| Policy or skill | 20 Hz (every 25 physics steps) | TCP target pose plus gripper command |
| Agent (planner and verifier) | event-driven, per skill | skill calls |

### 3.4 Action and observation spaces

- **Learned-policy action (5-D):** an absolute TCP target in the `base` frame, given as position (3) plus yaw (1) with the gripper pointing straight down, plus a gripper command (1). Top-down grasps are enough for cubes and a bowl, and they avoid rotation-representation problems. ACT predicts absolute targets, and the Diffusion Policy paper reports that position control beats velocity control. IK and the position servos (§3.3) track this target. The VLA uses the same action space, so it compares directly with ACT.
- **Residual-RL action:** a bounded delta on top of the expert's target, for example ±2 cm and ±10° yaw.
- **Image-policy observation:** front RGB plus wrist RGB (128×128 by default, 224×224 only if needed), plus proprioception (joint positions, TCP pose, gripper width).
- **State-policy observation:** proprioception, object poses (noisy in the hard variant), target pose, and gripper state.
- BC, ACT, and Diffusion Policy are **not** language-conditioned. Object identities that define a task are therefore fixed by color for them (T4: red on blue). The VLA (T3-L) and the agent layer (T5) handle language references.

### 3.5 Conventions (fix on day one, in `docs/conventions.md`)

- SI units and radians everywhere.
- Frames: `world`, `base`, `ee` (the TCP site), `cam_front`, `cam_wrist`.
- Quaternions are **w, x, y, z** (MuJoCo). SciPy's `Rotation` defaults to **x, y, z, w**, so always pass `scalar_first=True` or convert in one helper.
- `data.xmat` and `data.site_xmat` are row-major 9-vectors: use `reshape(3, 3)`.
- One seeding utility is used everywhere, with separate seed ranges for training, validation, and evaluation (§9).

## 4. System architecture

Four layers. Each one runs on its own and is evaluated on its own. The architecture diagram is in [roadmap.md §2](roadmap.md#2-architecture).

1. **Physics and robot.** A MuJoCo scene, built with `MjSpec`, containing the Panda, a table, colored cubes, a bowl, a front camera, and a wrist camera.
2. **Motion and skills.** Off-the-shelf IK (`mink`) and MuJoCo's position servos, wrapped as parameterized skills and a scripted expert.
3. **Learned policies.** RL (PPO) trained from scratch into an expert, imitation learning (BC, ACT, Diffusion Policy) and a fine-tuned VLA (SmolVLA) trained on that RL expert's demonstrations, and residual PPO refining the RL expert under perturbed dynamics.
4. **Agent layer.** A VLM grounds objects in the camera image, an LLM planner emits a JSON plan of skill calls, and a verifier checks each result and triggers retry or replanning. The agent's action API is the **skill library**, executed either by scripted skills or by the fine-tuned VLA (Phase 4).

## 5. Tasks

### 5.1 Task suite (difficulty ladder)

| ID | Task | Randomization | Example success predicate (freeze before results) | Time limit |
| --- | --- | --- | --- | --- |
| T1 | Reach a target point | target position | TCP within 5 mm of target | 5 s |
| T2 | Pick a cube and place it in a target zone | cube pose, zone pose | cube center within 3 cm of zone center (xy), at rest, released | 15 s |
| T3 | Pick a cube and place it in a bowl | cube and bowl poses, cube color | cube inside the bowl volume, at rest, released | 15 s |
| T3-L | "Put the {color} cube in the bowl", with 2-3 cubes of different colors | poses, colors, which cube is named, instruction wording | named cube inside the bowl, other cubes moved less than 2 cm | 15 s |
| T4 | Stack cube A (red) on cube B (blue) | both poses | A resting on B's top face within 1.5 cm (xy), stable for 1 s after release | 20 s |
| T5 | Multi-step language instructions combining T2-T4 | all of the above plus distractors | goal predicate for each instruction (§8, Phase 4) | 60 s |

### 5.2 Randomization levels

- **L0:** fixed scene.
- **L1:** object and target poses.
- **L2:** L1 plus lighting, textures, distractor objects, small camera pose jitter, and small friction and mass perturbations.

### 5.3 Hard variant T2-H (for RL)

T2 with a **tight placement tolerance** (1 cm and 10° yaw), **unmodeled dynamics** (cube mass ×[0.5, 3], friction ×[0.5, 1.5], hidden from the expert), and **observation noise** on object pose (σ ≈ 5 mm in position, 3° in yaw). Before training anything, check that the scripted expert has headroom here: its success should land between 40% and 75%. Tune the perturbation magnitudes until it does, then freeze the definition.

## 6. Environment and stack

### 6.1 Software

- **Python 3.12.** Current LeRobot requires Python ≥ 3.12. Use `uv` with a lockfile.
- **`mujoco`** (pin a 3.x version that `mink` supports) and **`mink`** for IK.
- **MuJoCo Menagerie** as a git submodule pinned to a specific commit. It is not a pip package; `robot_descriptions` is an alternative that fetches it.
- **PyTorch ≥ 2.10** with the MPS backend. LeRobot itself accepts older versions, but ≥ 2.10 pairs with a `torchcodec` that supports Homebrew's current `ffmpeg`.
- **`lerobot`** (pinned), with the `training`, `diffusion`, and `smolvla` extras. Install `ffmpeg` via Homebrew.
- **`gymnasium`** and **`stable-baselines3`**.
- **Local models:** `mlx-lm` and `mlx-vlm`, or Ollama or LM Studio. Each exposes an OpenAI-compatible server.
- **`pydantic`** for the plan schema, the **`openai`** client for OpenAI-compatible model servers, and `pytest`.
- Plain YAML plus dataclasses for configs (or Hydra), and TensorBoard or Weights & Biases for logging.

**Environment split.** Run the simulation and training stack (`mujoco`, `torch`, `lerobot`, `sb3`) in one environment. Run model serving (MLX, Ollama, or LM Studio) in a separate process and environment, reached over HTTP. This avoids dependency conflicts. It also means switching between local and frontier models is only a config change.

### 6.2 macOS notes

- `mujoco.viewer.launch_passive` requires the `mjpython` launcher on macOS. For quick inspection, run `python -m mujoco.viewer --mjcf=path.xml`.
- Offscreen `mujoco.Renderer` works on macOS without setup. Do not set `MUJOCO_GL=egl` or `osmesa`; those backends are Linux-only. In multiprocess environments, create the renderer **inside** each worker.
- Set `PYTORCH_ENABLE_MPS_FALLBACK=1` so unsupported MPS ops fall back to the CPU.
- MJX (JAX) and MuJoCo Warp target accelerators and give no useful speedup here. Use CPU MuJoCo with multiprocess vectorized environments (start with 8-10 workers and benchmark).
- Run long jobs under `caffeinate -i` so the machine does not sleep.
- CI on a Linux runner covers the unit tests and state-only smoke tests. Mark rendering tests and run them locally.

### 6.3 Compute and memory plan

| Workload | Where | Typical cost (measured values are recorded in `decisions.md`) |
| --- | --- | --- |
| Physics, scripted evaluation, demo generation | CPU, multiprocess | minutes to about an hour per batch |
| BC and ACT training | MPS | hours per run |
| Diffusion Policy | MPS or a rented GPU | several times slower than ACT |
| State-based PPO | CPU, 8-10 processes | hours per run, capped at 2 days |
| Local LLM and VLM | MLX on unified memory | seconds per call, hours per ablation cell |
| Frontier API rows | network | roughly tens of dollars in total; log token usage |
| SmolVLA fine-tunes | short MPS run first, then a rented GPU if needed | about 15-25 GPU-hours, roughly $15-75 |

**36 GB:** keep only one large model in memory at a time, and never alongside a training job. **18 GB:** use only the small VLM (4B-8B class) for both grounding and planning, and lean on API models for the ceiling rows.

## 8. Phase plan

The project is built in seven phases. Each phase ends with exit criteria that must hold before the next one starts.

### Phase 0: Setup and scene

**Build.**

- Repo, environment, pinned dependencies, and the Menagerie submodule.
- Scene via `MjSpec`: Panda, table, cubes, bowl, target zone, front and wrist cameras, and TCP site.
- `docs/conventions.md`, `docs/decisions.md`, and one seeding utility.
- Measure physics steps per second and render frames per second, and record them.

**Exit criteria.** The scene compiles and both cameras render. `make setup` works in a clean environment.

### Phase 1: Environment and scripted expert

**Build.**

- **Motion:** `mink` with a frame task on the TCP site, a posture task, and joint limits, solved on a robot-only model at 100 Hz. MuJoCo's position servos track the resulting joint targets.
- **Waypoints:** linear interpolation between TCP targets with a maximum TCP speed.
- **Gripper and contacts:** a grasp counts as successful when both fingers touch the target object (from `data.contact`), the gripper is not fully closed, and a lift check passes. Tune contacts: cubes of about 4-5 cm and 50-100 g, `cone="elliptic"` with `impratio` > 1, and `condim` ≥ 4 on fingertips and cubes to reduce slip and spinning. Record the final values.
- **Skills:** `reach(pose)`, `grasp(obj)`, `place(pose)`, `pick_and_place(obj, destination)`, and `stack(a, b)`. Each has preconditions, a postcondition check, a timeout, and a structured result with a success flag and a failure reason. The agent's planner calls `pick_and_place` and `stack`, and its verifier reuses the postcondition checks.
- **Scripted expert:** a closed-loop state machine that composes skills from oracle object poses and solves T2-T4. It recomputes each action from the current state, which Phase 2's noise injection relies on.
- **Environment API (Gymnasium):** `reset(seed)`, `step(action)`, `observe()`, `success()`, and randomization configs for L0-L2. The visual parts of L2 can be finished in Phase 2.
- **Evaluation harness:** one `Policy` interface for every method, parallel evaluation, JSON results, Wilson and bootstrap confidence intervals, and a report script.

**Evaluate.** Run the scripted expert on T1-T4 × L0-L2, 100 episodes per cell on fixed evaluation seeds. Produce a failure breakdown: IK failure or unreachable target, grasp miss, slip, collision, placement error, timeout.

**Exit criteria.** T1 ≥ 99%. T2 and T3 ≥ 90% at L1. T4 ≥ 70% at L1. IK solves random workspace targets, the arm settles within 2 mm of a held target, and the same seed reproduces the same episode. A script writes the results to `eval/results/`.

In practice, the scripted expert's measured success fell short of T3 and T4's exit criteria. Rather than keep hand-tuning the state machine, Phase 1b trains an RL policy on the same tasks to replace it as the demonstrator; the scripted expert remains in the benchmark as a baseline.

### Phase 1b: Reinforcement learning (training an RL expert)

**Build.**

- **Pure PPO, not residual RL,** trained from scratch per task, covering every non-language task (T1, T2, T3, T4), so the result does not inherit the scripted expert's failure modes. T3-L and T5 need language conditioning and stay out of scope; they keep using the scripted expert (§8, Phase 2, "Language-labeled demos"). Reuse Phase 3's state-based environment design (below) without the T2-H perturbations: proprioception, the target object's own pose (not hard-coded by color, so one policy per task generalizes to naming an arbitrary object among distractors), the destination pose, and relative vectors, with a staged dense reward (reach, grasp, lift, place) plus a sparse success bonus. T1 has no object: its observation and reward collapse to TCP-to-target distance only.
- Train with `SubprocVecEnv`, 8-10 workers, the same PPO hyperparameters as Phase 3's pure-RL arm. Budget up to 10-20 M environment steps per task, capped at 2 days wall-clock.

**Evaluate.** Run the Phase 1 evaluation harness on each trained policy, on the same evaluation seeds as the scripted expert's Phase 1 baseline.

**Exit criteria.** Every non-language task (T1, T2, T3, T4) has a frozen RL-expert checkpoint that meets the Phase 1 exit criteria for that task and clearly exceeds the scripted expert's measured rate. Wrap each in the `Policy` interface so it is a drop-in demonstrator for Phase 2 (T2, T3) and base policy for Phase 3's residual RL; T1's checkpoint has no downstream demo generation and exists only to confirm baseline parity. Any task that does not reach the target keeps the scripted expert as its baseline and demo source (§11).

### Phase 2: Imitation learning and VLA

#### 2a. Imitation learning

**Build.**

- **Demo generator:** run the frozen Phase 1b RL expert (falling back to the scripted expert for any task without a qualifying checkpoint) on training seeds that are disjoint from evaluation seeds. Record front and wrist RGB, proprioception, and the 5-D action. Keep only successful episodes and log the discard rate. During collection, inject DART-style noise: execute perturbed actions but label them with the clean expert action, so the demos contain recoveries and covariate shift drops. Target 400 successful demos each for T2 and T3. T4 is optional (see §12). Datasets and BC checkpoints already collected from the scripted expert are kept as a historical baseline, not regenerated.
- **Dataset writing:** use the LeRobot dataset API (`LeRobotDataset.create`, `add_frame`, `save_episode`) instead of writing files by hand. The on-disk format has changed between releases, so pin the version.
- **Policies:**
  - State BC (an MLP on oracle state). It bridges the comparison with RL.
  - Image BC (ResNet-18 plus an MLP). The simplest visual reference.
  - ACT via LeRobot (`lerobot-train` with the MPS device).
  - Diffusion Policy via LeRobot, using DDIM sampling with few denoising steps for fast inference.
  - **Fallback:** if LeRobot integration fails, use a minimal in-repo ACT (CVAE plus transformer).

**Experiments.**

- Data scaling for ACT on T2-L1: 25, 50, 100, 200, and 400 demos.
- Robustness: train on L1, test on L2, and test zero-shot on T2-H.
- ACT chunk size {1, 10, 50, 100}, with and without temporal ensembling. LeRobot's ACT uses a single observation frame, so the observation-history ablation applies only to Diffusion Policy (`n_obs_steps` 1 vs 2).

**Compute notes.** Benchmark iterations per second with a 1,000-step run first, then set step counts from that. Use 128 px images and a ResNet-18 backbone. Diffusion Policy trains several times slower than ACT, so it uses fewer training steps. If one run would take more than about 12 hours on MPS, rent a GPU for that run only. Note the model-size caps in the write-up.

**Exit criteria.** At least one image-based learned policy reaches ≥ 70% on T2-L1. The data-scaling curve and the L1-to-L2 robustness table exist.

#### 2b. VLA fine-tune

**Build.**

- **Language-labeled demos.** Store an instruction string per episode in the LeRobot dataset's `task` field, using templates with paraphrases ("put the red cube in the bowl", "place the red block into the bowl"). Generate 400 T3-L demos with the Phase 1b RL expert for T3, given each scene's named cube as the target object, in addition to the T2 and T3 demos.
- **Fine-tune SmolVLA** (LeRobot, starting from the pretrained base checkpoint) on T2, T3, and T3-L together, with the same cameras and 5-D action space as ACT. Check the camera keys and state and action dimensions the SmolVLA config expects.
- **Compute.** Run a short fine-tune on MPS to measure speed. If a full run would take more than about 12 hours, rent a 24-48 GB GPU for the fine-tunes (§6.3).

**Experiments.**

- SmolVLA vs ACT on T2-L1 and T3-L1, trained on the same demos.
- Data scaling: fine-tune on 100, 200, and 400 demos per task, and compare the curve with ACT's.
- Robustness: train on L1, test on L2 (lighting, textures, distractors), compared with ACT.
- Language grounding on T3-L: success rate and wrong-object rate.
- Generalization: unseen paraphrases and, optionally, unseen color names.
- End-to-end vs modular: SmolVLA vs the Phase 4 agent (planner plus scripted skills) on the same T3-L instructions and seeds. Run this once Phase 4 works.

**Exit criteria.** SmolVLA is evaluated on T2-L1, T3-L1, T2-L2, and T3-L with confidence intervals, its data-scaling curve exists, and its wrong-object rate is reported. No success threshold is set; results are reported as measured.

### Phase 3: Residual reinforcement learning under perturbed dynamics

**Build.**

- **T2-H** as defined in §5.3, with the Phase 1b RL expert's headroom check done and the definition frozen before any training. Because the RL expert is stronger than the scripted expert, expect to need harsher perturbations than an earlier scripted-expert-based calibration would have required.
- **State-based environments** (no images, for sample efficiency) using `SubprocVecEnv`. This is the same design Phase 1b introduced, with the T2-H perturbations added.
- **Pure RL on T2-H:** PPO (stable-baselines3) trained from scratch directly on the perturbed task, independent of the Phase 1b RL expert. Use a dense shaped reward (reach, grasp, lift, place) plus a sparse success bonus. Inspect rollout videos to catch reward hacking.
- **Residual RL:** $a = a_{expert}(s) + \mathrm{clip}(\pi(s), -\delta, \delta)$, where $a_{expert}$ is the frozen Phase 1b RL expert. Initialize the final layer near zero so training starts at the RL expert's performance. Use the same reward plus a small action penalty.
- **Throughput:** profile the environment step before running experiments, keep IK at 100 Hz, avoid per-step allocations, and record steps per second. Plan run budgets from that measured rate.

**Experiments.** Five training seeds per method. Budgets: 1-3 M environment steps for residual RL and up to about 10-20 M for pure PPO on T2-H, with a hard cap of 2 days of wall-clock per experiment. Produce learning curves (mean with a bootstrap CI across seeds), steps needed to reach the RL expert's success rate, and success on T2-H as a function of perturbation magnitude for the RL expert, residual RL, and pure PPO on T2-H (report the scripted expert's T2-H success too, for historical context). Pure PPO may not solve pick-and-place within this budget; the result is reported either way.

**Exit criteria.** Residual RL beats the Phase 1b RL expert on T2-H with statistical separation: the bootstrap CI of the difference, over seeds × episodes, excludes zero. Otherwise, document a negative result with a diagnosis.

### Phase 4: Agent layer

**Build, in this order.**

1. **Oracle perception.** Read the object list (name, color, pose) from the simulator. This is the upper bound and the debugging baseline.
2. **VLM grounding.**
   - Render front RGB and depth with `mujoco.Renderer`; depth comes out in meters.
   - Ask the VLM for a **point** (preferred) or a box for the referenced object. Coordinate conventions differ by model; for example, Qwen3-VL returns relative coordinates on a 0-1000 grid, while others return pixels. Normalize in one adapter and check it on a calibration image.
   - Back-project. Intrinsics come from `model.cam_fovy` (vertical FOV, **in degrees**; convert to radians): $f_y = (H/2)/\tan(\mathrm{fovy}/2)$, $f_x = f_y$, with the principal point at the image center. MuJoCo cameras look along −z with +y up (OpenGL convention), so convert to OpenCV axes before applying pinhole formulas. The camera-to-world transform comes from `data.cam_xpos` and `data.cam_xmat`. Use the median depth over a small patch.
   - **Test:** project known world points to pixels and back with analytic depth; the round-trip error must be below 1e-6 m. A second test using rendered depth must land within one pixel's footprint.
   - Report pixel error and metric error against the oracle.
3. **Planner.** The LLM receives the instruction, the grounded object list, and the skill API (`pick_and_place(object, destination)` and `stack(top, bottom)`) as a JSON schema. It emits a JSON plan, which Pydantic validates; retry on invalid output. Use constrained or structured decoding where the runtime supports it (Ollama and LM Studio both support JSON-schema outputs). Do not rely on native tool calling. The plan may contain `ask_clarification` or `refuse` for ambiguous or infeasible instructions.
4. **Verifier and recovery.** After each skill, check the result. In oracle mode, evaluate geometric predicates on the simulator state. In perception mode, re-ground and evaluate the same predicate on the estimated poses, and optionally ask the VLM a yes/no question; compare how reliable the two checks are. On failure, escalate: retry the skill, then re-ground, then replan with the failure reason. Allow at most 3 recoveries per instruction.
5. **Orchestrator.** Runs the plan, execute, and verify loop. It logs every prompt, response, plan, skill result, and key frame to JSONL. These logs drive the failure taxonomy and the demo video.
6. **VLA skill executor.** Implement `pick_and_place` a second way: turn the call into an instruction from SmolVLA's training distribution ("put the red cube in the bowl") and run the fine-tuned SmolVLA until the verifier's predicate holds or a timeout expires. The planner, verifier, and recovery stay the same.

**Instruction set.** 50 instructions covering:

- single-step ("put the red cube in the bowl")
- two-step
- stacking
- distractors
- spatial relations ("the cube left of the bowl")
- ambiguous instructions (should ask for clarification)
- infeasible instructions (should refuse)

Each instruction has a **goal predicate in code**, evaluated on the final simulator state rather than against a gold plan, so any valid plan counts. Run each instruction on 3 scene seeds. Also run the agent on the T3-L instructions and seeds for the comparison with SmolVLA (Phase 2b).

**Models (36 GB).**

- **Start:** one local VLM for both grounding and planning, for example Qwen3-VL-8B-Instruct at 4-bit (about 5-6 GB).
- **Upgrade:** Qwen3-VL-30B-A3B-Instruct at 4-bit for grounding (about 17-18 GB, about 3B active parameters, so it is fast). Add a text-only planner such as Qwen3-14B at 4-bit (about 8-9 GB) if planning is the bottleneck.
- Model choices are configuration, not code; newer releases (for example from the `mlx-community` Hugging Face organization) can replace these.

**Ablation matrix (the core result).**

| Perception | Planner | Purpose |
| --- | --- | --- |
| Oracle poses | Local LLM | planner quality in isolation |
| Local VLM | Local LLM | fully local system |
| Local VLM | Frontier API model | planner ceiling |
| Frontier API VLM | Frontier API model | overall ceiling |

**Executor comparison (oracle perception, local planner).** On the T3-L instructions and on two-step instructions whose steps match SmolVLA's training tasks, compare planner + scripted skills, planner + SmolVLA skills, and SmolVLA end to end. This measures what hierarchical planning adds to a VLA on longer instructions.

**Exit criteria.** The full instruction set × 3 seeds has been run for at least 2 cells, including oracle plus local LLM. A categorized failure taxonomy exists (perception, planning, execution, verification) with counts. The executor comparison is complete.

### Phase 5: Evaluation, write-up, packaging

- Freeze the benchmark: final seeds, final configs, and one command that regenerates every table and figure.
- Run the final evaluations for all methods with Wilson (success rates) or bootstrap (across seeds) 95% confidence intervals.
- Demo video, about 2 minutes: an instruction typed, the plan shown, the execution, one real failure and recovery, and the results table.
- README: architecture diagram, results, how to reproduce, limitations.
- Write-up: what was built, the key findings, and directions for future work.
- Repo hygiene: CI green, pinned requirements and lockfile, license, documented seeds.

## 9. Evaluation protocol

- **Seeds.** Use separate seed ranges for training, validation, and evaluation, defined in config. Evaluation seeds are never used for training or tuning.
- **Episodes per cell.**
  - Scripted and state-based methods: at least 100.
  - Image policies: at least 50.
  - RL: 5 training seeds × 100 evaluation episodes.
  - Agent: 50 instructions × 3 scene seeds.
- **Precision.** The 95% Wilson half-width at 50% success is about ±13 percentage points with n = 50, ±10 with n = 100, and ±7 with n = 200. Do not claim differences smaller than this. For RL, variance across seeds usually dominates, so bootstrap over seeds.
- **Success.** Task-specific geometric predicates, written in code before any results are seen (§5.1).
- **Metrics.**
  - Success rate with a 95% CI, mean completion time, and collision count.
  - Steps to expert-level success (RL).
  - Agent: instruction success, steps to success, replan rate, and failure category.
- **Main benchmark table.**
  - Rows: scripted expert, state BC, image BC, ACT, Diffusion Policy, SmolVLA, pure PPO, residual PPO. "Pure PPO" is the Phase 1b RL expert (also the demonstrator behind every imitation-learning row); "residual PPO" is Phase 3's refinement of it.
  - **Shared columns:** T2-L1 and T2-H; every method is evaluated on both.
  - Extra columns: T3-L1, T4-L1, and T2-L2 for the methods whose observations support them, and T3-L for SmolVLA and the agent. Mark unsupported cells N/A explicitly.
  - Further columns: observation modality, training data (demos or environment steps), and training compute (CPU, MPS, or GPU hours).
- **Fairness.** Every method gets the same scene, seeds, action limits, and episode time limit.
- **Reporting.** Every table and figure is generated by a script from `eval/results/*.json`. No number is pasted by hand.

## 10. Development principles

1. **Tests guard conventions.** Silent errors dominate robotics code: wrong frame, degrees vs radians, quaternion order, transposed rotations, OpenGL vs OpenCV camera axes. Unit tests with known answers and round-trip tests catch these, and no module is built on until its tests pass.
2. **Every run is reproducible.** The config, git commit, seeds, and dataset version are stored with each run.
3. **Results come from scripts.** Every reported number is generated from `eval/results/*.json`.
4. **Decisions are logged.** `docs/decisions.md` records the action space, observations, reward terms, backends, contact parameters, and the reasons for each.

## 11. Risks and mitigations

| Risk | Likelihood | Mitigation |
| --- | --- | --- |
| Grasping is unreliable (slip, penetration, spinning) | High | Elliptic cones with `impratio`, `condim`, and `solref` tuning; lift check and regrasp; larger or lighter cubes; simpler object geometry |
| Frame or convention bugs | High | Unit tests, projection round-trip tests, `conventions.md` |
| Dependency conflicts (LeRobot pins vs the MLX stack) | Medium | Separate environments; models behind an HTTP API; lockfile |
| LeRobot API or dataset-format churn | Medium | Pin the version; use the dataset API; fall back to a minimal in-repo ACT |
| SmolVLA fine-tune slow on MPS, or setup friction | Medium | Short MPS benchmark first; rent a GPU for the full run; pin LeRobot |
| MPS slow or unsupported ops | Medium | 128 px images, ResNet-18, fallback flag, fewer steps; rent a GPU for specific runs |
| Python control loop too slow for RL | Medium | Profile; IK only at 100 Hz; more worker processes |
| Phase 1b RL expert does not beat the scripted expert on some task | Medium | Keep the scripted expert as that task's demo source; proceed with the remaining tasks |
| T2-H too easy, leaving no headroom for RL | Medium | Headroom check before training; freeze the definition |
| Residual RL fails to learn | Medium | Fall back to the Phase 1b RL expert alone, reward shaping, curriculum; report the result |
| VLM grounding is poor on rendered scenes | Medium | Points instead of boxes, high-contrast colors, bigger objects, a coordinate-convention test, API VLM comparison, oracle baseline |
| Local model memory pressure | Medium | One large model at a time; smaller variants; separate processes |
| IK library integration stalls | Low | Drive the hand with a mocap body welded to it, with the arm actuators removed |

## 13. Future work

- **Larger VLA.** Fine-tune π0 or π0.5 (supported in LeRobot) on a rented GPU and compare it with SmolVLA.
- **Standard benchmark.** Fine-tune and evaluate SmolVLA on LIBERO with LeRobot, for comparability with published results. LIBERO requires Linux, so run it on a rented machine.
